# 002. Мультитенантность через PostgreSQL RLS

**Статус:** accepted
**Дата:** 2026-04-15

## Контекст

Платформа должна обслуживать множество проектов (тенантов) — разные тематики, каналы, настройки. В будущем — продажа как SaaS другим бизнесам. Необходима надёжная изоляция данных.

## Решение

**Shared Database + Row Level Security (RLS).**

- Все таблицы содержат `tenant_id UUID NOT NULL`
- PostgreSQL RLS policies фильтруют данные на уровне БД
- Middleware автоматически устанавливает `set_config('app.current_tenant', ...)` в каждой сессии
- Индексы: `tenant_id` — первая колонка в composite indexes

## Альтернативы

| Вариант | Причина отказа |
|---------|---------------|
| Database-per-tenant | Операционно дорого, сложные миграции при масштабе |
| Schema-per-tenant | Лучше изоляция, но миграции по N схемам — кошмар |
| Application-level WHERE | Опасно — человеческий фактор, забытый WHERE = утечка |

## Последствия

**Плюсы:**
- Изоляция enforced на уровне БД (нельзя случайно прочитать чужие данные)
- Одна схема, одна миграция — просто масштабировать
- Эффективное использование ресурсов

**Минусы:**
- Нужно аккуратно управлять connection pool (session variable per connection)
- Не подходит для строгого compliance (SOC2 может требовать физическую изоляцию)
- При очень большом количестве тенантов (10,000+) может потребоваться шардинг
